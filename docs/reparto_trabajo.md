# Propuesta de reparto del trabajo

> **Estado:** propuesta para debatir. No hay responsables asignados todavía.

## 1. Criterios para repartir

1. **Experiencia actual:** qué conocimientos puede aportar cada persona.
2. **Dificultad de la historia:** qué conceptos nuevos exige.
3. **Aprendizaje:** que todas las personas puedan desarrollar y probar código.
4. **Interés:** qué funcionalidades le gustaría aprender o asumir a cada integrante.
5. **Dependencias:** qué necesita cada historia para poder desarrollarse e integrarse.

No se trata de repartir el mismo número de historias, sino de buscar una carga razonable y oportunidades de aprendizaje para todos.

## 2. Primera tanda propuesta

Se propone empezar con las cuatro primeras historias de la fase 1:

| Historia | Funcionalidad | Perfil al que se propone inicialmente |
|---|---|---|

Esta distribución es orientativa y debe revisarse con todas las personas. La US-05 (modificar socios) también tiene prioridad Must y deberá planificarse en esta primera etapa, aunque no se propone asignarla hasta conversar con el equipo.

## 3. Colaboración

- Cada historia tendrá una persona responsable de llevarla de principio a fin: programarla, probarla y poder explicar cómo funciona.
- La persona responsable puede pedir ayuda o proponer **pair programming** (trabajo en pareja para resolver una tarea y aprender conjuntamente).
- En una sesión de pair programming, quien tiene asignada la historia debe participar activamente en la escritura y comprensión del código.
- Cada Pull Request debe ser revisado por otra persona.
- La experiencia de una persona puede ayudar al resto, pero no debe convertirla en responsable de resolver todas las partes complejas.

Con esa información se repartirán las siguientes historias.
